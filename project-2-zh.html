匯率自動化與多來源資料整合

背景與問題

財務／作業人員過去需要手動查詢多個銀行與政府網站（中央銀行、台灣銀行、關務署電子申報系統、CNYES） 以取得每日與每旬（10 天一次）的匯率，再手動輸入 GL 系統，單次作業約需 30 分鐘。 此外，只要遇到假日有匯率需要更新，人員就得在假日登入處理，形成持續性的加班負擔。 專案目標是自動化整個「查詢→登錄」流程，消除這類重複性人工作業。

角色與挑戰

擔任角色：Automation Engineer / Developer — 獨自負責整個管線從設計、開發到部署的全流程， 並搭配 AI 輔助開發工具（Claude Code）與 Python 進行開發。

利害關係人

  • 財務／GL 團隊（資料使用者）
  • 主管／管理層（專案發起與監督）

限制條件

  • 沒有共用程式模組，每支腳本刻意設計為獨立、自成一體
  • 多個資料來源使用不同的爬取方式，穩定度各異
  • 沒有自動化測試套件，各腳本使用不同的資料庫連線函式庫（pymssql/pyodbc、Oracle thick/thin mode）

風險

  • 來源網站改版或新增機器人偵測機制，可能讓爬蟲悄悄失效
  • Oracle 寫入效能／穩定性問題
  • 缺料日需要正確的回補邏輯，而不是直接讓整個管線失敗

方法與解決方案

  • 優先採用穩定的結構化來源（CSV/JSON API）而非頁面爬取，只要來源有提供就使用（中央銀行、台灣銀行 CSV API、關務署 JSON API），只有在來源必須靠 JavaScript 渲染時（CNYES）才使用 Selenium/Playwright。
  • 以 Playwright 建立截圖機制，搭配真實 Chrome User-Agent、domcontentloaded 等待策略與明確的元素等待，繞過台灣銀行的 Akamai 機器人偵測挑戰，在不中斷管線的情況下保留稽核用截圖。
  • 以冪等（idempotent）的 MERGE 語法將資料寫入 SQL Server 的 GL 介接表，同時寫入雙向匯率（例如 USD→TWD 與 TWD→USD），並計算以 USD 為基準的交叉匯率。
  • 新增以設定檔驅動的 Oracle 多目標寫入機制（oracle_active_env / oracle_insert_targets），讓單次執行就能同時寫入 UAT/Test/Prod 多個 Oracle 環境，不需要為每個環境各寫一支腳本。
  • 建立自動化 Excel 報表產出與 Email 通知機制（成功/失敗各自獨立收件人清單），讓財務團隊不需要查 log 也能掌握執行狀況。
  • 以 Docker 容器化整個管線並排程自動執行 — 銀行匯率每日執行、旬別/入口網站匯率每 10 天執行一次 — 完全移除假日人工介入的需求。
  • 全程使用 AI 輔助開發（Claude Code）加速疊代，用於排查機器人偵測失效、Oracle 寫入異常、交叉匯率計算錯誤等問題。

關鍵決策與取捨

決策

刻意讓每支 Import*.py 腳本保持獨立、不抽共用模組。

為什麼

在沒有測試套件、單人維護的情況下，共用模組一旦出錯可能同時拖垮所有管線； 犧牲長期的程式碼重用性，換取更低的迴歸風險，是更安全的選擇。

犧牲了什麼

接受各腳本之間存在一定程度的程式碼重複，換取故障隔離——單一管線的問題不會擴散到其他管線。

另外兩個決策也依循同樣的邏輯：能用 CSV/JSON API 就不用 Selenium（前期需要多花力氣找出各銀行穩定可用的 API 端點，換取長期執行更穩定、更快速），以及採用回補（lookback）機制而非缺料就直接失敗 （優先確保管線持續運作，而非堅持當日資料的絕對即時性，避免來源短暫異常就擋住後續 GL 入帳）。 以設定檔驅動多環境 Oracle 寫入，則是增加設定檔的複雜度，換取消除 UAT/Prod 之間重複的寫入邏輯。

交付物與價值

交付物

  • 涵蓋 4 個資料來源、11 種幣別的自動化匯率擷取管線（3 支腳本）
  • SQL Server + Oracle 雙寫入 GL 介接整合，支援多環境
  • 自動產出含截圖稽核軌跡的 Excel 報表
  • 成功/失敗分流的 Email 通知系統
  • Docker 容器化、排程執行（每日 + 每旬週期）

價值

  • 單次匯率查詢與登錄作業時間從約 30 分鐘降至約 5 分鐘（減少約 83%）
  • 每日與每旬匯率週期完全自動化執行，徹底消除假日人工維護作業
  • 上線後運作穩定：上線半年內僅發生 2 次異常（一次為 Oracle 寫入效能異常、一次為台灣銀行網站改版），皆透過 AI 輔助排查快速定位並修復

體悟

自動化串接第三方網站是一項持續性的維運工作，而非一次性的開發任務。 即使管線已相對穩定，上線半年內仍遇到來源網站改版；AI 輔助疊代讓這類問題能快速排查修復， 而不至於造成長時間中斷。在沒有測試套件、單人維護的情況下，選擇讓腳本保持獨立 （接受部分程式碼重複）而非過早抽象成共用模組，實務上獲得驗證：半年內僅 2 次異常，且都沒有跨管線擴散。 這個專案真正的價值，不在於自動化邏輯本身，而在於消除了一項反覆發生的人力依賴——假日人工維護匯率—— 這才是原本最大的作業痛點。
