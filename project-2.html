Exchange Rate Automation & Multi-Source Data Integration

Business Context & Problem

Finance and operations staff previously had to manually check multiple bank and government websites (Central Bank of the ROC, Bank of Taiwan, the customs portal, CNYES) to look up daily and 10-day (旬) FX rates, then manually key them into the GL system — roughly 30 minutes per run. This manual process also required staff to log in on weekends and holidays whenever a rate needed updating, creating a recurring overtime burden. The goal was to eliminate this manual, repetitive workload by automating the entire lookup-to-entry pipeline.

My Role & Key Challenges

My role: Automation Engineer / Developer — solely responsible for end-to-end design, development, and deployment of the pipeline, using AI-assisted development (Claude Code) alongside Python.

Stakeholders

  • Finance / GL team (data consumers)
  • Management (project sponsor / oversight)

Constraints

  • No shared codebase/module — each script self-contained by design
  • Heterogeneous data sources, each with different scraping methods and reliability
  • No automated test suite; differing DB client libraries across scripts (pymssql/pyodbc, Oracle thick/thin mode)

Risks

  • Source websites changing structure or adding bot detection could silently break scrapers
  • Oracle write performance/reliability
  • Missing-data days needing correct fallback logic instead of hard-failing the pipeline

Approach & Solution

  • Prioritized stable structured endpoints (CSV/JSON APIs) over UI scraping wherever a source offered them (CBC, TCB CSV API, customs portal JSON), reserving Selenium/Playwright for sources that only render via JavaScript (CNYES).
  • Built Playwright-based screenshot capture with a real Chrome user-agent, domcontentloaded wait, and explicit selector wait to bypass Bank of Taiwan's Akamai bot challenge, preserving audit-proof screenshots without blocking the pipeline.
  • Implemented idempotent MERGE-based upserts into the SQL Server GL interface table, writing bidirectional rate pairs (e.g. USD→TWD and TWD→USD) plus USD-based cross-rate derivation.
  • Added a config-driven multi-target Oracle insert layer (oracle_active_env / oracle_insert_targets) so a single run can fan out writes across UAT/Test/Prod Oracle environments without duplicating scripts.
  • Built automated Excel report generation and email notification (separate success/failure recipient lists) so the finance team gets visibility without checking logs.
  • Containerized the pipeline with Docker and scheduled it to run automatically — daily for bank rates, every 10 days for portal/monthly-basis rates — removing the need for manual weekend/holiday intervention.
  • Used AI-assisted development (Claude Code) throughout for rapid iteration when diagnosing bot-detection failures, Oracle write issues, and cross-rate calculation bugs.

Key Decisions & Trade-offs

Decision

Kept each Import*.py script fully self-contained rather than extracting a shared module.

Why

With no test suite and a solo maintainer, a bug in a shared module could have silently broken all pipelines at once. Trading long-term DRY-ness for lower regression risk was the safer call.

What we gave up

Some code duplication across scripts — accepted in exchange for isolating failures so a bug in one pipeline can't cascade into the others.

Two more decisions followed the same logic: choosing CSV/JSON API scraping over Selenium wherever possible (extra up-front effort to find stable API endpoints, in exchange for materially more reliable, faster runs long-term), and using a lookback fallback instead of hard-failing on missing rate days (favoring pipeline continuity over strict same-day data freshness, so a temporary source outage wouldn't block downstream GL posting). Config-driven multi-environment Oracle writes added some config complexity in exchange for eliminating duplicated insert logic across UAT/Prod.

Deliverables & Impact

Deliverables

  • Automated FX rate ingestion pipeline (3 scripts) covering 11 currencies from 4 data sources
  • SQL Server + Oracle dual-write GL interface integration with multi-environment support
  • Auto-generated Excel reports with inline screenshot audit trail
  • Success/failure email notification system
  • Dockerized, scheduled deployment (daily + 10-day cycles)

Impact

  • Reduced manual FX rate lookup-and-entry time from ~30 minutes to ~5 minutes per run (~83% reduction)
  • Fully automated daily and 10-day (旬) rate cycles, eliminating weekend/holiday manual maintenance work entirely
  • Highly stable in production: only 2 incidents in 6 months since go-live (an Oracle write performance anomaly, and a Bank of Taiwan website redesign) — both diagnosed and resolved quickly via AI-assisted debugging

Lessons Learned

Automating around third-party websites is an ongoing maintenance commitment, not a one-time build. Even a stable pipeline hit a source website redesign within 6 months, and AI-assisted iteration made recovering from it fast rather than disruptive. Keeping scripts self-contained — accepting some duplication over premature shared abstractions — paid off in practice: with no test suite and a solo maintainer, only 2 incidents occurred in 6 months, and neither cascaded across pipelines. Ultimately, the highest-value outcome wasn't the automation logic itself, but removing a recurring human dependency — weekend/holiday manual rate maintenance — which had been the real operational pain point.
