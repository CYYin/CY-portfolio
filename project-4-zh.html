金仁寶 SRM-ERP 訂單整合平台

問題

金仁寶（Kinpo）供應商開放 API 與 Sercomm 內部 SRM/ERP 系統之間， 採購單與訂單變更通知並未整合，需要人工審核與登錄。這不僅拖慢了對訂單變更的 回應速度，也提高了在供應商變更期限內延誤處理的風險，更難以即時評估訂單 是否符合產能可行性。

解決方案

我建構了一套全端訂單整合平台，串接金仁寶供應商開放 API 與 Sercomm 內部 SRM、ERP 系統。平台透過簽章 API 呼叫接收進來的採購單與訂單變更（POC）通知， 並套用商業規則 — 包含 70 天變更期限與基於 APS 的可行性評估 — 自動產生 接受、變更或拒絕的回應。核准的訂單透過 PL/SQL MERGE/INSERT 管線同步至 Oracle ERP，並具備逐筆提交與重試機制以確保可靠性。系統以 FastAPI 為核心， 搭配 Celery/Redis 進行非同步任務調度、APScheduler 執行每週 APS 快照工作， 並維持雙資料庫架構 — SQL Server 儲存 SRM 資料、Oracle 儲存 ERP 資料 — 同時具備自動化錯誤追蹤、Email 警示，以及供訂單與日誌檢視的 Vue 3 管理後台。

技術棧

  • Python 與 FastAPI
  • Celery 與 Redis（非同步任務調度）
  • APScheduler（排程式 APS 快照工作）
  • SQL Server（SRM 資料）與 Oracle（ERP 資料，PL/SQL MERGE/INSERT）
  • REST API 整合（簽章 API 呼叫）
  • Vue 3（管理後台）
  • 自動化錯誤追蹤與 Email 警示

我的角色

我同時擔任專案負責人與主要開發者，從 API 整合、商業規則設計到資料庫同步策略 與管理後台，全程主導系統架構設計。我也與供應鏈及 ERP 相關利害關係人密切合作， 共同訂定平台內建的接受規則與可行性判斷邏輯。

成效／指標

  • 自動產生進單採購單與訂單變更的回應
  • 透過規則式的接受／變更／拒絕邏輯，大幅降低人工審核工作量
  • 以逐筆提交與重試機制提升 ERP 同步的可靠性

標籤
