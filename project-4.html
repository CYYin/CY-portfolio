HCL Notes to SQL Server BPM Data Migration & Sync Platform

Business Context & Problem

Sercomm had 300+ BPM forms scattered across multiple HCL Notes 12 NSF databases. This historical data was locked inside the Notes platform, unreachable for SQL-based reporting, analytics, or cross-system integration, and some Notes applications were already headed for retirement with no systematic way to preserve or migrate their data. These forms had also been built independently by different departments over the years, with no unified documentation of field naming, semantics, or data types. Manually inventorying and rebuilding schemas form-by-form at a scale of 300+ would have been prohibitively costly and impossible to schedule reliably. What was needed was a scalable, repeatable automation approach that could coexist with the live Notes system — historical import plus ongoing incremental sync.

My Role & Key Challenges

My role: ETL / data migration platform developer — responsible for DRAPI integration, designing the AI-assisted field-semantics analysis process, building out the SQL Server/Oracle target side, and operating and debugging the ongoing incremental sync mechanism.

Stakeholders

  • Department business owners (field mapping review)
  • IT (database and network environment)
  • HCL Notes system administrators

Constraints

  • Legacy Notes forms lacked documentation; field naming was inconsistent
  • Some forms had conditional fields (the same label resolving to different actual fields depending on an upstream selection)
  • Data was only reachable via DRAPI, with no direct access to the underlying NSF; mandatory business review meant the process couldn't be fully automated

Risks

  • Data migration: an Active View's definition could silently diverge from the actual data range, risking incomplete migrations if not verified per-form
  • AI accuracy: inferring Chinese/English mappings and data types across tens of thousands of fields still required human review to catch errors
  • Sync reliability: Notes' native unread/markRead mechanism was unreliable on some scopes, risking missed or duplicate read-marking

Approach & Solution

The architecture followed a two-phase model: schema build → business review → data sync.

  • Called the Domino REST API (DRAPI) form2view endpoint to retrieve each form's Active View field list.
  • Used the Claude AI API to semantically analyze fields in batches of 50, inferring Chinese/English mappings, data types, and Master/Detail structure, and producing a Column Mapping Excel sheet for business review.
  • Once approved, auto-generated and ran CREATE TABLE statements, using DXL (Notes Designer's exported form design files) to resolve keyword-field code-to-display-text mappings and handle multi-value fields (list-type → junction table, tag-type → comma-separated string).
  • After the full historical import, a scheduler triggered incremental sync by sync_group (hourly/daily/weekly/monthly): DRAPI's unreadOnly=true fetched unread documents, markRead=true marked them as read as a natural checkpoint/resume mechanism, and SQL Server/Oracle performed UPSERTs keyed on notes_unid with soft-delete support.
  • A central control table (Notes_System_List) drove the whole process through a Migration_Step state machine (0 → 1.1–1.9), keeping progress for all 300+ forms trackable and re-runnable.

Key Decisions & Trade-offs

Decision

Replace purely manual field-mapping work with "AI semantic analysis + human review."

This dramatically shortened the inventory timeline for 300+ forms, at the cost of adding an Excel review checkpoint (Migration_Step 1.5) to keep business sign-off in the loop — the process couldn't run fully hands-off.

Other key trade-offs

The sync mechanism reused Notes' native unread/markRead behavior instead of building a separate change-data-capture log: this saved development cost and naturally supported checkpoint/resume, but markRead behavior was unreliable on some scopes (e.g. B011), requiring a separate recovery script (recover_b011_failed_unids.py) to catch missed syncs.

When old and new Active Views conflicted, I chose the cleaner, more current view (e.g. M003 used TESTEXPORT instead of the stale but fully-historical Form1View) — trading "one-shot full history coverage" for correctness in the live sync data; when historical data was genuinely needed (e.g. a 2023 lookup), I queried the old view live via DRAPI instead of polluting the production sync table.

Every migrated target table shares a standardized set of sync columns (notes_unid, notes_created, notes_modified, is_deleted, etc.), letting the incremental sync engine be reused across 300+ tables — at the cost of needing ALTER TABLE on some legacy tables to add missing columns for compatibility (e.g. a missing approver column).

Deliverables & Impact

Deliverables

  • A DRAPI client wrapper (token management, pagination, error retry)
  • A Claude AI field-semantics analysis pipeline (Chinese/English mapping, type inference, Master/Detail detection)
  • A Column Mapping Excel review workflow (pending review → approved → auto table creation)
  • A full initial import plus incremental sync engine (supporting SQL Server and Oracle as dual targets)
  • A central-control-table-driven migration state machine (Migration_Step 0–1.9)
  • Sync audit logging and failure alerting (notes_sync_log plus email notifications)

Impact

  • Converted historical BPM data previously locked in Notes into SQL-queryable, report-ready structured data, enabling cross-system analysis
  • Eliminated the manual effort of designing schemas form-by-form — the AI-plus-review model dramatically accelerated field inventory across 300+ forms
  • Established a sustainable, near-real-time incremental sync mechanism rather than a one-time cutover
  • The framework proved extensible — already expanded to support Oracle as a target (e.g. the A011 system) and multiple coexisting systems (PartNumber, DWNotes, etc.)

Lessons Learned

A legacy platform's "Active View" definition can silently drift from the actual data range it covers — assumptions made before migration must be re-validated against the live view at execution time, not trusted from an earlier schema snapshot. AI can dramatically accelerate large-scale field-semantics analysis, but what actually makes an automated pipeline trustworthy enough to ship is a mandatory human review checkpoint, not model accuracy alone. Relying on a platform's native mechanism (like Notes' unread/read state) as a sync checkpoint is convenient, but reliability varies by table — a sync system's design should focus on detecting and recovering missed syncs, not just handling the happy path.
